# ADR 005 — BCF: our own reader and writer, not `@ifc-lite/bcf`

**Status:** accepted · **Date:** 2026-09-04 · **Phase:** 7

## Context

Phase 7 needs to import `.bcf` / `.bcfzip` (BCF 3.0 primary, reading 2.1 and
upgrading on import) and export a **valid** BCF 3.0 archive.

`@ifc-lite/bcf` is already a dependency — it ships `readBCF` and `writeBCF`,
plus viewpoint helpers, and it is from the same family as the IFC engine we
chose in ADR 001. Using it would have been the cheap answer.

## Decision

**Implement `lib/bcf/` ourselves**, on `DOMParser` and `fflate`, and vendor the
official buildingSMART XSDs to validate what we write.

`@ifc-lite/bcf` is not used. The `no-restricted-imports` rule in
`eslint.config.mjs` already blocks `@ifc-lite/*` outside the IFC adapter, so no
new enforcement was needed.

## Why

### 1. Its reader parses XML with regular expressions, and BCF nests ambiguously

This is not a style objection. BCF reuses element names at different depths in
ways a pattern cannot distinguish:

- A comment's **text** child is also called `<Comment>`:
  `<Comment Guid="…"><Comment>text</Comment></Comment>`.
- BCF 3.0's viewpoint **container** is `<Viewpoints>` — the same word 2.1 uses
  for each viewpoint **entry**. They differ only by which one carries a `Guid`.
- 2.1 writes `<Labels>text</Labels>` repeatedly; 3.0 writes
  `<Labels><Label>text</Label></Labels>`.

That last one is a live defect, not a hypothetical. `@ifc-lite/bcf` matches
labels with `/<Labels>([^<]+)<\/Labels>/g`, which cannot match 3.0's form
because the content begins with `<`. Verified:

```
3.0 <Labels><Label>Architecture</Label></Labels>  →  []
2.1 <Labels>Architecture</Labels>                 →  ["Architecture"]
```

**Every label in every BCF 3.0 file is silently dropped.** Filtering topics by
label is an explicit Phase 7 requirement, and the failure is invisible: the file
imports, the topics appear, and the label filter is simply always empty.

`DOMParser` is available in the browser and under jsdom, and `lib/ids/parse.ts`
already uses it. The tree is what disambiguates these cases.

### 2. It would add a second zip library

`@ifc-lite/bcf` depends on `jszip`. We already use `fflate`, which is
substantially smaller and is what `lib/ids` and the OPFS layer use. Shipping
both to parse the same kind of archive is hard to justify in a browser-first
app.

### 3. Correctness here is checkable, so it should be checked

The requirement is a *valid* BCF 3.0 file. We vendored the seven XSDs from
`buildingSMART/BCF-XML @ release_3_0` into `lib/bcf/schema/` and validate the
written archive with libxml2 (the same `xmllint-wasm` the IDS module uses).

Writing the schema from memory would have been wrong in at least six places.
The schema settled all of these against what a reasonable person would guess:

| Guess | Actual |
|---|---|
| `<Header><File>` | 3.0 wraps them: `<Header><Files><File>` |
| `TopicType` / `TopicStatus` optional | **required** attributes |
| Viewpoint camera optional | the `xs:choice` has no `minOccurs="0"` — **required** |
| `AspectRatio` optional | **required**, and `PositiveDouble` (> 0) |
| `ViewSetupHints` under `<Components>` | it lives inside `<Visibility>` |
| `<Color>` holds `<Component>` children | 3.0 adds a `<Components>` wrapper |
| GUIDs are case-insensitive | `[a-f0-9]{8}-…` — **lowercase only** |
| Empty elements are fine | `NonEmptyOrBlankString` rejects them |

The GUID casing one matters in practice: plenty of tools write uppercase GUIDs,
so the writer lowercases them — and because a substitution in one place would
break `RelatedTopic` links, comment→viewpoint links and document references,
every GUID goes through one map (`GuidMap` in `serialize.ts`).

### 4. The 2.1 → 3.0 colour change is invisible to a validator

2.1 documents an 8-digit colour as **ARGB**. 3.0's schema annotates the same
attribute with `FF00FF99`, i.e. **RGBA**. Both are "8 hex digits" to a
validator, so an upgraded file would come out quietly the wrong colour with
everything reporting success. `parse.ts` reorders against the source version.

## Consequences

- ~1,400 lines of reader, writer, merge, filter and viewpoint conversion to
  maintain ourselves, covered by 113 unit tests and 17 browser tests.
- Every archive in `fixtures/bcf/` — 20 of buildingSMART's own test cases across
  2.1 and 3.0 — is parsed, rewritten, and validated against the XSDs on every
  `npm test`. "Exports a valid BCF 3.0 zip" is a checked fact.
- We carry the schemas. They are regenerated by
  `npx tsx scripts/bundle-bcf-schema.mts` and are inlined so validation needs no
  network, which the privacy line requires anyway.
- `@ifc-lite/bcf` stays in `package.json` as a transitive concern only. If its
  reader is rewritten on a real XML parser, this decision is worth revisiting —
  the viewpoint and overlay helpers are genuinely useful.

## Alternatives considered

**Use `@ifc-lite/bcf` and patch the label bug upstream.** The label regex is one
symptom of the approach, not the whole of it; the comment and viewpoint
ambiguities are structural. A fix would mean replacing its parser, which is this
decision by a longer route.

**Use `@ifc-lite/bcf` for reading and write ourselves.** Splits the round-trip
across two models of the data and doubles the vocabulary. The reader is the part
with the defects, so this keeps the wrong half.
